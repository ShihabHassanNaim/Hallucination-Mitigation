The problem

Slide 02 · Problem

Retrieval-Augmented Generation (RAG) systems still hallucinate — even when the answer is in the retrieved evidence.

What is a hallucination?
A model-generated statement that is not supported by the source it claims to ground itself in — factually wrong, fabricated, or contradicted by the retrieved evidence.
Why it matters
In domains like medicine, law, and finance a hallucinated fact is a liability. Users can't tell which sentences are grounded and which are fabricated.

Symptoms in modern RAG

  • The LLM paraphrases retrieved text and drops qualifiers ("always" → "sometimes").
  • The LLM adds facts that are consistent with its prior but absent from the corpus.
  • The LLM denies facts that are actually present (false abstention).

→ Existing solutions are either retrieval-only (rerankers) or detection-only (NLI). Neither closes the loop.

Motivation & research questions

Slide 03 · Motivation

The goal: build a single, end-to-end pipeline that detects, verifies, and explains hallucinations — and that exposes a clean, machine-readable justification for every decision.

Research questions

RQ1
Can a hybrid retriever (dense + sparse + cross-encoder rerank) reliably surface the evidence the NLI verifier needs?
RQ2
Does atomic claim verification (split → retrieve → NLI → fuse) outperform whole-answer verification?
RQ3
Can we explain every gate decision (PASS / REGEN / ABSTAIN) with the evidence that drove it?
Design principle: every component must load its real HuggingFace checkpoint — no mocks, no stubs. The system either runs against real models or it raises.

Contributions

Slide 04 · Contributions
  1. End-to-end 13-step architecture — query understanding → grounded generation → early detection → claim extraction → hybrid retrieval → rerank → NLI → fusion → regeneration → gate → explainable response → evaluation.
  2. Real-model implementation — 6 first-class HuggingFace components (BGE-M3, BGE-Reranker-v2, mDeBERTa-v3-NLI, GLiNER, Llama-3.1-8B-Instruct, Qwen). No silent fallback to stubs.
  3. Atomic-claim verification — every generated sentence is split, retrieved against, and judged by NLI; final decision fuses per-claim verdicts via EEDC + temperature scaling.
  4. Explainable output — every step writes a trace; final response is JSON + Markdown + HTML with per-claim evidence and verdicts.
  5. Evaluation framework — 13 metrics across 10 categories (HRR, CCR, VSR, BLEU, ROUGE-L, BERTScore, ROC-AUC, MRR, nDCG, …) computed automatically by scripts/evaluate_full.py.
  6. Web UI + REST API — Flask chat-style demo, project tree viewer, evaluation dashboard, FastAPI mirror; live / degraded status badge per component.

Deep dive · Detection & Confidence

Slide 08 · Steps 3 + 4

Step 3 · Early Hallucination Detection

  • Compute cosine similarity between the answer embedding and the concatenated evidence embedding with BGE-M3.
  • Feed (cosine, answer length, evidence length, claim-count, named-entity overlap) into an XGBoost classifier trained on labeled pairs.
  • Output: p_hallucination ∈ [0, 1] + a 3-class verdict (supported / weak / contradicted).
Why early? if the early detector says "high hallucination risk", the gate can skip the expensive retrieval + NLI steps and ABSTAIN cheaply.

Step 4 · Confidence Assessment (EEDC)

  • EEDC = Expected Evidence-Disagreement Calibration. Combines the answer's perplexity, the NLI verifier's entropy, and the retrieval score.
  • Platt scaling + temperature scaling fit on a held-out calibration set (scripts/calibrate_eedc.py).
  • Output: calibrated confidence in [0, 1] that is comparable across queries.
Why calibrate? raw model scores are not probabilities. Without calibration the gate either over-accepts or over-abstains.

Deep dive · Retrieval & Verification

Slide 09 · Steps 6 + 8

Step 6 · Hybrid Retrieval

  • Dense: BGE-M3 embeddings → FAISS (cosine, top-50).
  • Sparse: rank_bm25 over the same chunks (top-50).
  • Fuse with Reciprocal Rank Fusion (RRF, k = 60). RRF is parameter-free and beat simple linear blending on our dev set.
  • Returns top-5 chunks by RRF score.
Why hybrid? BM25 catches exact terms (names, years) that dense retrieval misses; dense catches paraphrases that BM25 misses. RRF merges them without learning weights.

Step 8 · NLI Verification

  • Cross-encoder: MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7.
  • For each (claim, evidence) pair → 3-way softmax over entailment / neutral / contradiction.
  • Step 7 (BGE-Reranker-v2) reorders the top-5 first, so the NLI sees the strongest evidence at the top.
  • Per-claim verdict: supported / unknown / contradicted.
Why claim-level? a single entailment on the whole answer can hide a contradictory half. Split → verify → fuse gives the gate an auditable signal.

Evaluation setup

Slide 11 · Setup

Dataset

  • 69 synthetic QA pairs built into src/utils/data_loader.py — each row has query / answer / evidence / label.
  • Mix of factoid, definitional, and intentionally-wrong rows to stress the verifier (e.g. "Eric Arthur Blair was French").
  • Indexed corpus = 6 hand-written documents (d0…d5).

Metrics

  • BASE (10): claim P/R/F1, retrieval R@5 / P@5 / MRR / nDCG, VSR, end-to-end accuracy, confidence.
  • FULL (7 extras): detection accuracy / P / R / F1, ROC-AUC, hallucination reduction rate (HRR), claim correction rate (CCR).

Pipeline

python -m scripts.build_index --corpus synthetic --out data/index
python -m scripts.run_inference --query "..."
python -m scripts.evaluate       --synth --out data/metrics.json
python -m scripts.evaluate_full  --synth --out data/metrics.json
python -m scripts.calibrate_eedc --out data/calibration.json

Reproducibility

  • All knobs in configs/default.yaml; override via env vars prefixed HALLUC_.
  • 31-test pytest suite uses in-memory fakes → fast + offline.
  • Production code always loads the real HF checkpoint.

Analysis & discussion

Slide 13 · Analysis

What's working

  • Retrieval is strong — R@5 = 79.7%, MRR = 79.7%. The hybrid BGE-M3 + BM25 + RRF combination reliably surfaces the right evidence.
  • Verification always returns a usable verdict (VSR = 100%) — no crashes, no skipped claims.
  • Decision diversity — the gate exercises all three branches (23 PASS / 10 REGEN / 36 ABSTAIN), so it's not degenerating to one class.

What's hurting E2E accuracy

  • Conservative gate: a high ABSTAIN rate (52%) drags E2E accuracy down — the gate refuses too often even when the answer is correct.
  • Claim split: Claim F1 = 24% means the rule-based splitter misses facts that the LLM later verifies (precision + recall both low).
  • High retrieval precision, low end-to-end: the gap between R@5 (79.7%) and E2E (34.4%) is the verification + gate loss — the next bottleneck to close.
RQ answers (preliminary):
  1. Yes — hybrid retrieval reliably supplies evidence (R@5 ≈ 80%).
  2. Partial — atomic claim verification is auditable but the splitter is the weakest link.
  3. Yes — every gate decision carries the evidence that justified it, surfaced in the JSON payload.

Limitations & future work

Slide 14 · Limitations
LimitationImpactNext step
Synthetic-only evaluation Numbers may not transfer to open-domain corpora Evaluate on HaluEval QA + a curated real-world RAG log
Llama-3.1 is gated Default generator swaps to Qwen 3 without a HF token Auto-fallback + transparent degraded mode badge (already shipped)
Single-hop retrieval Can't answer queries that require chaining evidence Step 6.5: query-decomposition + iterative retrieval
Rule-based claim splitter Drives the low Claim F1 (24%) Fine-tune a small claim-segmentation model or prompt-tune Llama 3.1
No human evaluation Don't know how users perceive REGEN / ABSTAIN Run a small user study: prefer answer vs prefer ABSTAIN
Detection metrics require evaluate_full.py HRR / CCR / ROC-AUC are absent from the BASE run Document + auto-run after every evaluate.py in CI

Bottom line: the architecture closes the loop, the gate is safe, and the retrieval is strong — the open frontier is claim-level understanding.
